# govengers/events: design

Status: E1-E11 agreed 31.10.2026 together with govengers/jobs (their source is `docs/design.md` of github.com/govengers/jobs, section 3); E12 onwards decided while building v0 (15.11.2026). Decisions are numbered; a later change gets a new number, never a rewrite.

`govengers/events` publishes facts from one govengers service to others on top of `govengers/jobs`. Profile `library`, Apache 2.0, Go 1.26, PostgreSQL 18; govengers/standards apply.

## 1. The model

**Jobs stay inside a service, events cross services, and an event arrives as a job.** Once delivered, an event needs exactly what a job already has (lease, retry, backoff, dead letter, wide event, metrics), so events add routing and transport only, and both sides of the wire process through the job runtime.

| Producer and consumer | Mechanism | Hop |
|-----------------------|-----------|-----|
| module of a modular monolith reacts to another module | local subscription: Publish enqueues the subscriber's job in the publisher's transaction | none, exactly-once enqueue |
| different services, own databases | remote subscription: Publish records a delivery in the ledger and enqueues its outbound job; the job POSTs a signed CloudEvent to the subscriber's inbox, which enqueues the subscriber's job | one HTTP hop, at least once, deduplicated at the inbox |

```
publisher                                         subscriber
  Publish(tx) --> ledger row + outbound job          inbox: verify, dedup (inbox row), enqueue handler job
                  outbound job --POST signed-->      handler job (jobs: retries, wide event, metrics)
  RegistrationHandler <--PUT set of subscriptions--  registration job (at startup, retried)
```

## 2. Decisions E1-E11 (agreed with jobs)

| ID | Decision |
|----|----------|
| E1 | Module `github.com/govengers/events`, depends on `govengers/jobs`. A separate module, so the younger events API can change without forcing a jobs major (LIB-001). |
| E2 | Typed contract `events.NewTopic[P]("orders.order-placed.v1")` in a contract package of the publisher that depends on nothing beyond the standard library and uuid; subscribers import it. The major version is part of the name; within a version only additive changes; a breaking change publishes v1 and v2 side by side until every subscriber moved. |
| E3 | Envelope: CloudEvents 1.0, structured JSON mode: `id` (uuidv7), `source` (publisher service), `type` (topic), `time`, `data`, extensions `traceparent` and `actor`. |
| E4 | Publish on the caller's transaction: reads the topic's subscriptions and enqueues one job per subscription in that transaction. A topic without subscriptions stores nothing. (Queues refined by E13, the ledger by E15.) |
| E5 | Subscriptions live in the publisher's database. A subscriber declares its complete set per publisher and the publisher replaces that subscriber's rows in one transaction, so a removed handler stops receiving. Local: written at startup (same database). Remote: `PUT {publisher}/events/subscribers/{subscriber}` from a job, retried until the publisher answers, so the subscriber starts while the publisher is down. Events published before a subscription exists are not delivered. |
| E6 | Outbound delivery: loads the subscription at send time (deleted: complete and drop) and POSTs `application/cloudevents+json`, signed per Standard Webhooks (HMAC-SHA256). 2xx completes. 404 (subscriber mid-rollout), 408, 429, 5xx and transport errors retry with backoff; other 4xx are dead. 30 attempts, backoff capped at 1 h, about one day. |
| E7 | Inbox: verifies the signature and that the event type is the subscription's topic, then in one transaction inserts `(subscription, event id)` into `govengers_event_inbox` and, only when that row is new, enqueues the handler's job. 202 for new and duplicate deliveries alike. Inbox rows expire after 7 d, longer than E6's delivery window. |
| E8 | A subscription's signing secret is HMAC(subscriber's inbox key, subscription name). The subscriber sends it at registration and stores nothing; the publisher stores it. Rotating the key re-registers. The registration authenticates with the subscriber's API key at the publisher; an authorization check in the publisher's options decides which topics a subscriber may read. |
| E9 | The `actor` extension is audit information only. A subscriber's job runs as the subscriber's system identity; an identity issued by another service is never treated as authenticated. |
| E10 | Delivery is at least once and unordered. Payloads carry the aggregate's version or update time, so a subscriber can drop a stale update. |
| E11 | Packages: `events` (topics, envelope, signing, delivery, inbox and registration handlers on `net/http`), `events/postgresadapter` (Publish, stores, DDL), `events/ginadapter` (routes; dropped by E21). |

## 3. Decisions from v0

| ID | Decision |
|----|----------|
| E12 | One `events.Bus` per process instead of a publisher and a subscriber type: a service usually publishes and subscribes, and both roles register job handlers on the same worker (a second registration of one kind is an error). `events.New(&Options{Name, Store, Worker, ...})` registers the delivery, registration and sweep handlers; `events.Subscribe(bus, topic, handler, &SubscribeOptions{...})` declares a subscription and registers its handler; `bus.Register(ctx)` writes the local set and enqueues the registrations. Publish stays on `postgresadapter.Store` (E11): it takes the caller's pgx transaction, which the core must not import. The core declares `events.Store`; `postgresadapter.Store` implements it. |
| E13 | (refines E4) Queues: the library's own jobs (deliver, register, sweep) share one queue, `events.Queue` = `govengers.events`, so a service adds one queue to its worker, not three. A subscription's handler job is kind `events.<subscriber>.<subscription>` on queue `events.<subscriber>` (`events.SubscriberQueue`), one poller per subscriber instead of one per subscription; `SubscribeOptions.Queue` isolates a heavy subscription. The handler's attempts and backoff come from `SubscribeOptions`; a local subscription stores its queue and attempts with its row, so the publisher enqueues the right job. |
| E14 | (refines E5) A subscription is identified by `(subscriber, name)`; names are local to the subscriber (`create-invoice`, not `billing.create-invoice`), lower-case words joined by dots or hyphens, at most 100 characters. Remote publishers are declared in `Options.Publishers` (name, events base URL, API key) and referenced by name in `SubscribeOptions.Publisher`; every declared publisher is sent its set at `Register`, an empty one included, which removes a subscriber's last subscription there. `Register` writes the local set even when it is empty, for the same reason. |
| E15 | (refines E4's "no event log table") Delivery ledger `govengers_event_deliveries`: Publish writes one row per remote subscription and event with the encoded envelope, and the outbound job's payload is only the key (subscriber, subscription, event id) and a generation, so jobs carry references (J2) and a redelivery needs no event log. The event is stored as `bytea`, the exact bytes Publish checked, so every attempt sends what was measured (jsonb would re-serialise it larger). The ledger makes each (subscription, event) exactly once on the sender side: only a pending row of the job's generation is sent, `Redeliver` counts the generation up, so a second job of the same delivery (an older generation waiting for its backoff, a run after the record) sends nothing; only a run that dies between the POST and the record sends twice, which the inbox absorbs. The ledger has no foreign key to its subscription: a re-registration that removes a subscription must never fail a publisher's business transaction on a constraint; the outbound job records a delivery whose subscription is gone, local or of another topic now as failed without a request and without counting it (E18), so it does not stay pending and unswept. Local subscriptions need no ledger: their job is enqueued exactly once in the publishing transaction. |
| E16 | (implements E6, E8) Signing follows Standard Webhooks exactly (`webhook-id`, `webhook-timestamp`, `webhook-signature: v1,<base64>`, HMAC-SHA256 over `id.timestamp.body`, secrets `whsec_<base64>`), checked against the specification's test vector, so any Standard Webhooks library can receive from a govengers publisher. `webhook-id` is the event id. `Verify` runs on the raw body before anything parses it, accepts any of several space-separated signatures (rotation) and refuses timestamps more than 5 minutes away. `DeriveSecret(inboxKey, name)` is E8's secret; `NewSecret` gives an application a random one for a webhook it creates itself. |
| E17 | (refines E6) A 429 with `Retry-After` in seconds snoozes the job for that long, capped at 1 h; a snooze does not spend a job attempt, so the ledger's own attempt count bounds it: the attempt that reaches `DeliveryAttempts` (30) is final whichever counter reached it. A request refused by the HTTP client's address check (E19) or answered by a redirect past `MaximumRedirects` is permanent: retrying for a day only hides the misconfiguration. 401 and 403 retry like 404: they are what an inbox key rotation (until the registration with the new secrets arrived) and a rollout (replicas with different keys) answer, and a permanent 401 would count towards the auto-disable and lose every event published while disabled. Only the status is recorded, never the response body. |
| E18 | Auto-disable: a remote subscription is disabled after `Options.DisableAfter` (default 5) deliveries in a row ended failed; a delivered one resets the count. Counting failed deliveries, not failed attempts, makes the rule time-based without a clock: each failed delivery spent its retry window (about 19 hours) or was refused outright, so a high-volume subscription is not disabled by one bad minute and a refusing endpoint (400, 410) is disabled after five events. Only the transition from pending to failed counts, so a job that runs again after its record counts nothing twice; a failure the subscriber did not cause (the subscription disabled or obsolete, the delivery not loadable at its last attempt) does not count. A disabled subscription is skipped by Publish (its events are not recorded) and its pending deliveries are recorded as failed without being sent. A registration enables a subscription that failures disabled (the subscriber's sign of life, or a fixed endpoint), never one an administrator disabled (`disabled_by`); a registration without an admin-disabled subscription keeps the row, so dropping and re-adding it does not lift the disable. |
| E19 | `safehttp`: the outbound client checks the address in the dialer's `Control`, after DNS resolution, so a name that resolves to an internal address is refused on every connection and every redirect (DNS rebinding). Loopback, link-local (incl. the cloud metadata services), unspecified, multicast, the known metadata addresses and the NAT64/6to4/IPv4-compatible prefixes are always refused; private networks (RFC 1918, unique local, shared address space) only with `AllowPrivateNetworks`; `AllowedNetworks` narrows further and cannot lift the refusals. No proxy from the environment (a proxy would dial past the check), redirects followed only up to `MaximumRedirects` (default none), response bodies capped (default 1 MiB, an error instead of a silent truncation). The Bus's default client refuses private networks; a service delivering inside its cluster passes `safehttp.New(&safehttp.Options{AllowPrivateNetworks: true})` or an allowlist. |
| E20 | Secrets at rest: `postgresadapter` seals every remote subscription's secret through `events.Sealer` (`Seal(plaintext, associatedData)`, `Open(sealed, associatedData)`), without importing govengers/auth. auth's seal package has another method set (`Seal(seal.AssociatedData, []byte) (string, error)`, a struct that names purpose, table and row), which no interface here can match without the import; an application wraps its key ring in ten lines (docs/wiki/Security.md: purpose `webhook_signing_secret`, table `govengers_event_subscriptions`, row the associated data). The column stays `bytea`: it holds auth's sealed text and any other sealer's bytes. A `sealadapter` nested module can ship the wrapper once auth releases the seal package. The associated data is `govengers_event_subscriptions/<subscriber>/<name>`, so a sealed value moved to another row does not open. The sealer is required lazily: a store of a service with only local subscriptions needs none; storing or delivering a remote one without it fails with `ErrNoSealer`. |
| E21 | (replaces E11's `ginadapter`) The inbox and registration handlers take the subscription or subscriber from the last segment of the request path, so they mount under any router and prefix (`gin.WrapH(bus.InboxHandler())`) and the module needs no Gin dependency. The inbox is mounted without the application's authentication (the signature authenticates); the registration behind it (an API key), and `Options.Authorize(request, *RegistrationRequest)` decides; it sees the subscriber and every subscription with name, topic and endpoint (no secret), so the application can restrict where deliveries go, which matters with `AllowPrivateNetworks`; a struct, so it can grow. Nil refuses every registration; a registration naming the publisher itself is always refused (it would replace the publisher's local subscriptions). Registered endpoints, `InboxURL` and publisher URLs must be https unless `AllowHTTP`: a registration carries the API key and every signing secret. |
| E22 | (LIB-012) Tracing without an events `oteladapter`: Publish runs `jobs.Propagator.Inject` and writes `traceparent` and `tracestate` as CloudEvents extensions; the inbox runs `Extract` with them before it enqueues, so the jobs store's own propagator carries the trace into the handler's job. `jobs/oteladapter` gives the propagator and the attempt spans of delivery and handler jobs; an HTTP client span comes from wrapping `Options.HTTPClient`'s transport. The actor extension comes from `postgresadapter.Options.Actor`, a function of the context, so the module does not import govengers/auth. The `Observer` (`Published`, `DeliveryFinished`, `Received`, `Registered`) reports everything else; `prometheusadapter` counts it with closed label sets (an unknown subscription requested from outside is counted with an empty label). |
| E23 | (refines E7) The inbox answers 404 for an unknown subscription and for a local one (the publisher retries 404), 401 for a bad signature, 400 for a body that is not a CloudEvent 1.0 of the subscription's topic or whose id is longer than 200 bytes, 413 above `MaximumEventBytes` (E29, which Publish enforces too), 400 for an event with a NUL character. Accept pins READ COMMITTED: a concurrent second request of one delivery waits for the first's inbox row and then finds it, also on a server whose default isolation is REPEATABLE READ. |
| E24 | Retention: `events.SweepSchedule()` (a `jobs.Schedule`, hourly) deletes delivered deliveries after 7 days, failed ones after 30 and inbox keys after 7 (E7), in batches of 1000 per table, repeated in one run until none is left, so the retention holds whatever the traffic. The delivery batch locks with `SKIP LOCKED` and repeats its predicate on the deleted row, so a concurrent `Redeliver` keeps its row. Pending deliveries are kept, because the admin view needs them (a delivery whose job died outside the handler, e.g. a lost lease at the last attempt, stays pending until redelivered). |
| E25 | Admin operations on `postgresadapter.Store`, the application builds its view on them: `Subscriptions`, `DisableSubscription`, `EnableSubscription`, `Deliveries` (newest event first, keyset on the event id, which is a UUIDv7, so deliveries of one transaction with equal times page correctly), `Redeliver` (any status: reset to pending, attempts zero, next generation, and enqueue that generation's job in one transaction; an older job sends nothing). `Deliveries` has an index on `(event_id, subscriber, subscription)` for its order; a status filter scans it, which is fine while failures are not rare. An application creates webhooks for external receivers with `PutSubscriptions` and `NewSecret`, one subscriber per owner. |
| E26 | Postgres concurrency: `PutSubscriptions` takes a transaction-level advisory lock per subscriber and pins READ COMMITTED, so two replicas registering at once neither deadlock nor interleave their deletes (a test fails without the lock, and with the lock but REPEATABLE READ). `RecordDelivery` records only an attempt of the current generation, takes a pending delivery to any status and a failed one only to delivered, and reads the status before (`RETURNING old.status`, PostgreSQL 18) to count only a transition. Counting a failure and disabling happen in one statement under the row lock. |
| E28 | (refines E5) A registration job carries its set: the publisher, `InboxURL`, an ID of the inbox key (a hash, not the key) and the subscriptions' names and topics, never a secret. Every replica consumes `govengers.events`, the old ones of a rollout too; a set computed when the job runs would be the claiming replica's. The claiming replica derives the secrets from its inbox key, so it sends only a job with its key's ID and one of a publisher it declares; otherwise it retries, and a replica of the right version claims a later attempt. A registration job has no unique key (review round 3): a call coalesced into a pending job of its set would keep that job's older time, and a registration of another set made in between would win under E31 (new set, old set on a rollback, new set again: the publisher ended with the old one). N replicas starting together send N PUTs of the same set, each ordered by its own time. Two different sets in flight at once are ordered by E31. |
| E29 | `MaximumEventBytes` is 32 KiB. The handler's job carries the event (local subscriptions in the publishing transaction, remote ones from the inbox), and jobs refuses a payload above 256 KiB of jsonb (`pg_column_size`). jsonb takes up to six times the JSON text (an array of single digits: 12 bytes per element against 2, measured on PostgreSQL 18; empty arrays 2.7x, strings 1.3x), so 32 KiB fits in every shape, with the envelope. Raising it later needs the event out of the job payload (the inbox table holding the body, the job its key); a lower cap now is the direction that can be relaxed in a minor version. jsonb cannot store `\u0000` either: `EncodeData` refuses data with a NUL character (`ErrNulCharacter`), before Publish writes anything, and the inbox answers 400. |
| E30 | (D2 of review round 1) Deliveries, registrations and the sweep stay on one queue (E13). A separate delivery queue would protect registrations and the sweep, not one subscriber from another, which is the case that matters: a hanging endpoint holds a slot for the client's timeout per attempt. The README and the example give `events.Queue` a concurrency (8); isolation per subscription (pausing a subscription after consecutive failed attempts, before the ledger says failed) is additive later, a column in a later migration, and does not need a queue change. |
| E31 | (refines E5, E28; review round 2) A registration is ordered by the time `Register` was called (`Options.Now` of the registering replica), carried in the job's payload and the body as `registeredAt`. The publisher keeps each subscriber's newest time in `govengers_event_subscribers` and, under the subscriber's advisory lock, changes nothing for an older registration (`PutRegistration` reports false, the route answers 204, `Registration.Superseded`); the same time again applies, so a retry after a lost response works. An older job that retries after a newer one (an old pod started during a publisher outage, then a release) or two requests that arrive in reverse order no longer remove the newer set's subscriptions. A time ahead of the publisher's database clock is stored as `now()`, so a replica whose clock runs ahead cannot shut out the registrations after it. The price of that clamp: the comparison uses the unclamped time, so the order holds only while replicas' clocks differ from each other, and run ahead of the publisher's database clock, by less than the time between two registrations of different sets (review round 3; NTP keeps both within milliseconds). Rejected: the desired set in a table of the subscriber's database (fixes the backoff case, not two requests in flight in reverse order) and a sequence there (needs a store call in `Register` for no gain over clocks NTP keeps within milliseconds). `PutSubscriptions` stays unordered for applications' own webhooks and keeps the stored time. A body without `registeredAt` is not ordered. |
| E32 | (review round 2) The inbox answers 400 for an event PostgreSQL's jsonb cannot store, which the handler's job holds: `Accept` casts the received body to jsonb in its first statement and maps a data exception (SQLSTATE class 22: a NUL character, a lone surrogate escape, a number outside numeric's range, invalid UTF-8) to `ErrUnstorableEvent`. The delivery then fails at its first attempt instead of answering 500 thirty times. The cast is exact where a Go-side check of surrogates and numeric's range would be a second parser; it replaces the inbox's own NUL scan. Publish still checks only NUL characters (`EncodeData`); JSON a payload type passes through (`json.RawMessage`, `json.Number`) must be storable as jsonb, which the doc comments say. |
| E33 | (review round 2, rebutted finding) `Redeliver` does not wait for an attempt in flight: the old generation's request and the new one may reach the subscriber at the same time. Serializing them (a claim on the ledger row per attempt) would still send twice, because a redelivery is a second send by definition, and costs a write per attempt and a wait after a crash. Both requests carry the same `webhook-id` (the event ID), so the inbox enqueues the handler once (its key insert serializes the two), the old generation's record changes nothing, and the new one counts once; `TestARedeliveryWhileAnAttemptIsInFlightRunsTheHandlerOnce` holds this. A receiver outside govengers deduplicates by `webhook-id` as Standard Webhooks asks. |
| E27 | Tests: one embedded PostgreSQL per test binary, a fresh schema with both migrations per test (`internal/postgrestest`, copied from jobs); "two services, two databases" are two schemas and two `httptest` servers in one process; a retry waiting for its backoff is made due by SQL instead of sleeping. The end-to-end suite runs the shop example's two binaries (`examples/shop`) and is skipped when binaries, suite and inputs equal a green run (TST-015). |
| E34 | (replaces E27's harness) The tests run on `github.com/govengers/postgrestest` instead of a copy of jobs' harness: a database per test, copied from a template that the MigrationV1 of jobs and of events built once per server, instead of a schema migrated per test; "two services, two databases" are now two real databases. `internal/postgrestest` stays as a thin wrapper (`Main`, `New`, and the test `Sealer`), so the tests kept their code. `just test` runs under the library's launcher (`cmd/postgrestest`, at the version go.mod requires), one server for every test binary of the run; `go test ./<package>` alone and the e2e suite start one per binary as before. The binaries are unpacked once per machine into `~/.embedded-postgres-go/postgrestest` with the system tar, which CI restores, instead of the OS temp directory with the pure-Go xz decoder. Pinned to a pseudo-version of postgrestest's main until it is tagged. |

## 4. Packages

| Package | Holds | Depends on |
|---------|-------|-----------|
| `events` | `Topic`, `Event`, `Message`, signing, `Bus` (delivery, inbox, registration, sweep handlers), `Store`, `Sealer`, `Observer` | jobs, safehttp |
| `events/postgresadapter` | `Store`: Publish, subscriptions, ledger, inbox, sweep, admin; `MigrationV1` | pgx/v5, jobs/postgresadapter |
| `events/safehttp` | the SSRF-safe `http.Client` | standard library |
| `events/prometheusadapter` | Observer metrics | client_golang |

## 5. Not in v0, and when to add it

| Feature | Add when |
|---------|----------|
| event log table, replay to a new subscription | a subscriber needs history it was not subscribed for |
| batched deliveries, a broker adapter (NATS) | one POST per event per subscription is too expensive |
| per-subscription rate limits at the publisher | a subscriber needs protection beyond 429 and Retry-After |
| `Retry-After` as an HTTP date | a receiver sends one (rare for 429) |
| a separate client for application-created webhooks | a service delivers to its own cluster and to user-entered URLs from one Bus (today both use `Options.HTTPClient`) |
| a conformance suite for `events.Store` | a second implementation appears |
